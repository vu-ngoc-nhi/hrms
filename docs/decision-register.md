| C-34 | **Idempotency-Key semantics** for command endpoints that take an `Idempotency-Key`. (1) Same key + same payload: the business action executes once (no duplicate rows, events or audit); a retried or concurrent request receives the same logical successful result once the first execution completes, and never fails only because the first execution incremented `person.revision`. (2) Same key + different payload: rejected as `409 IDEMPOTENCY_KEY_REUSED`; the second action is not executed. (3) Different keys + same `expected_revision`: normal optimistic concurrency; one may succeed and the other receive `409 REVISION_CONFLICT`. Mechanism: the key is claimed first inside the business transaction, before the revision check. | Yes — verified for Create Employee and Assignment Change by explicit tests (commit `05ccd7d`); no code change was needed |

Minimum safe workflow; recovery as a first-class requirement; historical record ≠ operational effect; internal vs external dependencies; design for EmeSoft scale (scale down process complexity, not engineering quality); DB for invariants, services for workflows, UI for guidance; no speculative frameworks; design review questions and anti-patterns. Applies to all future design and implementation; does **not** reinterpret existing confirmed decisions — material conflicts are reported, not silently changed. Full text: `docs/design/emesoft-design-philosophy.md`; mandatory summary in `CLAUDE.md`. | Governance (documentation) |
| C-85 | **Access control direction (governance principle, follows C-84).** *Flexible role configuration, strict authorization enforcement.* Access is configured through roles and permissions, never hard-coded to individual users or organisational job titles; organisational position may suggest access but never silently determines privileges; adding or replacing HR staff should need role assignment only (no code change, migration or deployment).

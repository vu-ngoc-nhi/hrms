# Core HR internal API — conventions and status

The contract source is `src/contracts/core-hr/` (Zod registry and operation list). `contracts/core-hr/openapi.json` is generated by `npm run openapi:write`, and a test fails if it drifts from the code. Interactive docs are at `/internal/docs` and require `docs.read`.

## Conventions
- REST JSON under `/api/v1/core-hr/*`. UUID ids, snake_case fields, stable English enum values.
- Business dates are `YYYY-MM-DD`; timestamps are ISO 8601 with an offset. Employment status is computed for today in Asia/Ho_Chi_Minh.
- Paging: `page` starts at 1; `page_size` defaults to 20, maximum 100 (above that is 400). Lists return `{ data, total, page, page_size }`. Profiles are ordered by `employee_code`, then `id`.
- Errors return `{ error, message, request_id, details? }`. `message` is English and meant for developers. The UI displays text from its message catalog, keyed by `error` and `details[].code`.
  - 400 VALIDATION_ERROR / IDEMPOTENCY_KEY_REQUIRED
  - 401 UNAUTHENTICATED
  - 403 FORBIDDEN
  - 404 NOT_FOUND
  - 409 DUPLICATE_EMPLOYEE_CODE / DUPLICATE_CATALOG_CODE / WORK_EMAIL_IN_USE / IDEMPOTENCY_KEY_REUSED
  - 422 OPERATIONAL_PROFILE_INCOMPLETE / BUSINESS_RULE_VIOLATION / PROTECTED_FIELD_NOT_ENABLED
- Requests are strict: unknown fields return 400 `FIELD_NOT_ALLOWED`. Every response has `Cache-Control: no-store` and `X-Request-Id`.
- `POST /employees` requires an `Idempotency-Key` header, scoped per caller and operation.
  - A replay returns 201 with `Idempotent-Replayed: true` and re-reads the profile with the caller's current permissions.
  - The same key with a different payload returns 409.

Local-only endpoints, not in the spec, return 404 outside local/test: `GET /api/v1/dev/test-users` and `POST /api/v1/dev/test-tokens`.

Breaking changes made on 2026-10-08 (pre-production):
- `positions` → `job-titles` and `position_id` → `job_title_id`;
- `profile_state` removed; replaced by computed `completeness` and the optional `require_operational_completeness` flag;
- `employee_type_id` lives on the **employment period** (`employment.employee_type_id`), not the assignment (revision 2). Sending it inside `assignment` returns 400;
- employee types have `requires_work_email`;
- completeness items now include `work_email` or `contact_email` depending on the rule (C-10).
